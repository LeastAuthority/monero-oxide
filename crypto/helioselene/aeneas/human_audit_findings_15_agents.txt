===== AGENT 01: Invert step congruence (I.1) =====
SCOPE:
Audited `crypto/helioselene/src/field/verified/invert.rs`, especially `step`, mask/carry helpers, `MODULUS_XOR_TWO_MODULUS`, final shift/reduction/`CtOption`, and the Lean assumption in `crypto/helioselene/aeneas/HelioseleneCore/Spec/Invert.lean`.

FINDINGS: NONE

EVIDENCE:
`step` matches the Algorithm-1 shape assumed in Lean: odd/less-than masks at `invert.rs:35-47`, branch-free selects at `invert.rs:52-62` and `:167-168`, conditional `a-b` negation at `:63-78`, masked `u-v` at `:89-99`, sign/parity correction at `:111-136`, fused 0/1/2-modulus addition at `:140-165`, and final exact halving at `:170-172`.

The modulus split is correct: `MODULUS_XOR_TWO_MODULUS` at `invert.rs:127-128` equals `p ^ (2p)`. Low limbs reconstruct `2p`; high limbs differ from `p` only at bit 255, restored by `add_two_modulus << (Limb::BITS - 1)` at `invert.rs:164-165`. This also matches the Veridise Dafny constant/helper model in `Base.dfy` and the Algorithm-1 reference shape in ePrint 2020/972: https://eprint.iacr.org/2020/972.pdf.

Independent read-only Python simulation of the exact limb-level Rust arithmetic checked:
- 10,000 randomly generated `InvA`-valid states for 64-bit limbs and 10,000 for 32-bit limbs: invariant, parity/evenness, `u,v <= p`, congruences, gcd, and potential decrease all held.
- Full 510-step traces for 1006 inputs on 64-bit simulation and 206 on 32-bit simulation: zero input ended as payload `0`; nonzero inputs ended with `a=0`, `b=1`, `v*y ≡ 1 mod p`, and `v < p`.
- Loop count from `invert.rs:185-192` is 384 + 126 = 510 on 64-bit, and also simplifies to 510 on 32-bit.

Final behavior is consistent: `red1` conditionally subtracts `p` at `verified/mod.rs:59-66`; `invert` returns `CtOption::new(HelioseleneField(red1(v)), !value.is_zero())` at `invert.rs:194`; `is_zero` is the limb OR check at `verified/mod.rs:123-129`. `cargo test -p helioselene --lib` passed 11/11 tests.

EXPLOITABILITY / PROOF IMPACT:
No exploitable mismatch found. Under the assumed/reachable invariant, the branch-free step preserves the congruence and produces the expected inverse. If this assumption were false, `invert` has no self-validation and could return a wrong inverse with flag true, but I found no evidence of such a state.

RECOMMENDATIONS:
Discharge `step_congruence` in Lean. Add regression/property tests that check per-step invariant preservation on generated valid states, plus static assertions for `MODULUS_XOR_TWO_MODULUS == p ^ (2p)` and the 510 loop count.

RESIDUAL RISK:
The Lean theorem still depends on the `sorry`; the above is audit/testing evidence, not a proof. Formal coverage remains 64-bit-oriented, though the source-level arithmetic also checked out in 32-bit simulation.

===== AGENT 02: sqrt completeness and pow/sqrt ladders (I.2, IV.1) =====
SCOPE:
Audited `crypto/helioselene/src/field/verified/sqrt.rs` and `pow.rs`, with call-site context in `field/mod.rs` and `point.rs`. Reviewed prior Agent 01 report and prior audit artifacts; no duplicate finding.

FINDINGS: NONE

EVIDENCE:
`MODULUS_PLUS_ONE_DIV_FOUR` at `sqrt.rs:4-6` equals `(p+1)/4`; `p mod 4 = 3` from `field/mod.rs:25-26`. The table in `sqrt.rs:10-25` constructs `value^0..value^15` correctly. The prefix ladder at `sqrt.rs:27-58` computes `value^(2^128-1)`: `15 -> 255 -> 2^16-1 -> 2^32-1 -> 2^64-1 -> 2^128-1`.

The tail loop `sqrt.rs:59-71` processes exponent bits 124 down to 0: `to_le_bits().iter().take(253).rev().skip(128)` is MSB-to-LSB over the 253-bit exponent because `ff::FieldBits` is `BitArray<_, Lsb0>`. A read-only Python reconstruction of the exact prefix/tail/final-window schedule produced exactly `E = (p+1)/4`; all loop table indices stayed in `0..=15`, and the final unflushed window at `sqrt.rs:73-74` is handled correctly.

Even-root normalization is correct: `sqrt.rs:78` negates iff the candidate is odd; `subtle` implements this as constant-time conditional assignment to `-self`, and `HelioseleneField::neg` maps zero to zero at `verified/mod.rs:91-100`. The final gate `sqrt.rs:80` returns `Some` only when `res.square().ct_eq(value)`, so soundness is self-validating even if the ladder were wrong.

For `pow.rs`, the table at `pow.rs:5-20` is again `base^0..base^15`. The 256-bit loop `pow.rs:24-46` consumes bits MSB-to-LSB in 4-bit windows. Skipping the pre-squaring for `i == 3` is correct for the first window; every later window performs `res = res^16 * table[nibble]`. A read-only exponent-schedule simulation matched the input exponent for edge cases and 1000 random 256-bit exponents.

Constant-time indexing is appropriate: `pow.rs:37-42` scans all 16 table entries by `conditional_select`, so the secret `bits` value is not used as an array index. In `sqrt.rs:68,74`, direct indexing is driven only by the public constant exponent, not by secret field data. `u8_from_bool` at `src/lib.rs:11-20` is only used in `pow.rs` for secret exponent bits.

`recover_y` uses `curve_equation(x).sqrt()` at `point.rs:40-42`; `from_bytes` then applies the sign bit to the even root at `point.rs:360-362`. Thus sqrt completeness affects decompression acceptance, while the final self-check prevents accepting an invalid root. `cargo test -p helioselene --lib` and `cargo test -p helioselene --lib --release` both passed 11/11 tests.

EXPLOITABILITY / PROOF IMPACT:
No mismatch found. For reduced field inputs, `sqrt` computes the required candidate `a^((p+1)/4)`, so every square passes the final check; I.2 appears satisfied. A hypothetical sqrt ladder bug would fail closed on squares or nonsquares because of `res.square()==value`, affecting decompression completeness/availability, not soundness. No secret-dependent table index was found. `pow` satisfies its exponent contract, though it remains outside the Lean proof story.

RECOMMENDATIONS:
Discharge `sqrt_complete` in Lean using the exponent reconstruction above. Add small regression tests for `MODULUS_PLUS_ONE_DIV_FOUR == (p+1)/4`, sqrt of random squares, nonsquare rejection, even-root normalization, and inherent `HelioseleneField::pow` against a reference square-and-multiply implementation.

RESIDUAL RISK:
The conclusion relies on the existing reduced-field invariant and external primitive fidelity (`to_le_bits`, `conditional_select`, `ct_eq`). `pow.rs` is still un-translated/formally unproved in this artifact, and current crate tests do not directly target the inherent `HelioseleneField::pow(self, HelioseleneField)` path.

===== AGENT 03: crypto-bigint sbb/mac external fidelity (II.1-II.2) =====
SCOPE:
Audited II.1-II.2 only: Lean external models for `crypto-bigint` 0.5.5 `Uint::sbb`, `Limb::mac`, and the related `mul_wide`/`square_wide` product ordering used by helioselene field arithmetic.

FINDINGS: NONE

EVIDENCE:
Cargo resolves `crypto-bigint` to 0.5.5 at `Cargo.lock:178-181`.

Lean models 64-bit limbs explicitly: `TypesExternal.lean:36-55` models `Uint<LIMBS>` as little-endian `Array U64`; `FunsExternal.lean:28-35` defines `Limb::MAX` as all ones; `FunsExternal.lean:60-70` defines little-endian `toNat/ofNat`.

II.1 `sbb`: Lean models borrow-in as `borrow.val >>> 63` and borrow-out as `0` or all-ones at `FunsExternal.lean:662-696`. This matches the crate: `Limb::sbb` reads `borrow.0 >> (Self::BITS - 1)` and returns `(ret as Word, ret >> Self::BITS)` at `/home/user/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/crypto-bigint-0.5.5/src/limb/sub.rs:10-16`. On the 64-bit target, `Word = u64`, `WideWord = u128` at `src/limb.rs:48-54`, so an underflow produces high word `u64::MAX`. `Uint::sbb` just chains that limb borrow over little-endian limbs at `src/uint/sub.rs:11-22`.

Helioselene uses that full-mask convention correctly: `sub_value` calls `a.sbb(&b, Limb::ZERO)` at `crypto/helioselene/src/field/verified/mod.rs:53-55`; `red1` selects original vs reduced limbs using the returned borrow mask at `mod.rs:59-65`; field subtraction selects `candidate` vs `candidate + MODULUS` using the same full mask at `mod.rs:76-87`. `invert` mostly uses its own bounded 0/1 helper, explicitly documented as unlike `sbb` at `invert.rs:3-16`; its final `red1(v)` at `invert.rs:194` therefore inherits the verified `sbb` convention but no mismatch was found.

II.2 `mac`: Lean models `mac(a,b,c,carry)` as exact `a + b*c + carry`, returned as low 64 bits and high 64 bits at `FunsExternal.lean:229-256`. This matches `crypto-bigint` exactly: `Limb::mac` casts all inputs to `WideWord`, computes `ret = a + b*c + carry`, and returns `(ret as Word, ret >> Self::BITS)` at `src/limb/mul.rs:10-16`. The maximum value is `(2^64-1)^2 + 2*(2^64-1) = 2^128-1`, so the `u128` intermediate cannot overflow on the modeled target.

`mul_wide`/`square_wide` ordering also matches: Lean says `(lo, hi)` at `FunsExternal.lean:545-573` and `:575-602`. The crate documents and implements `(lo, hi)` at `src/uint/mul.rs:20-31` and returns `(lo, hi)` at `:66-67`; `square_wide` returns `(lo, hi)` at `:89-90` and `:160`. Helioselene’s `red512` expects exactly this order, copying `wide.0` into lower limbs and `wide.1` into upper limbs at `crypto/helioselene/src/field/verified/red.rs:38-40`; multiplication and squaring feed it directly at `verified/mod.rs:109-119`. The internal `red512` `mac` calls at `red.rs:49-55` and `:89-96` are consistent with low/high carry semantics.

Test evidence: `cargo test --manifest-path .../crypto-bigint-0.5.5/Cargo.toml --target-dir /tmp/crypto-bigint-0.5.5-audit-target --lib` passed 211/211 tests, including upstream `sbb_with_borrow` tests asserting `Limb::MAX` borrow-out (`src/limb/sub.rs:153-158`, `src/uint/sub.rs:170-175`) and `mul_wide` ordering tests (`src/uint/mul.rs:328-344`). `cargo test -p helioselene --lib` passed 11/11 tests, including reduction and field tests. Temporary build artifacts were removed.

EXPLOITABILITY / PROOF IMPACT:
No exploitable arithmetic bug or proof-invalidating mismatch found. The Lean field proofs’ subtraction/reduction and multiplication assumptions match the actual 0.5.5 dependency behavior on the modeled 64-bit target.

If these conventions had differed, impact would have been severe: `sbb` mask mismatch would break `red1`/field subtraction/final invert reduction; `mac` or `(lo,hi)` mismatch would invalidate `red512` and therefore all multiplication/squaring. That hypothetical does not apply to the current locked dependency.

RECOMMENDATIONS:
Add small dependency-fidelity regression tests in the audit/validation layer for: `sbb` with initial `Limb::MAX`, `sbb` underflow returning `Limb::MAX`, max-value `mac` returning `(MAX, MAX)`, and `U256::mul_wide/square_wide` low/high ordering into `red512`.

Keep the dependency pinned or re-run this check on any `crypto-bigint` upgrade, especially because `mul_wide` ordering changed in older pre-0.3 history.

RESIDUAL RISK:
The Lean artifact is 64-bit-specific. `crypto-bigint` also supports 32-bit limbs (`src/limb.rs:36-42`), whose analogous behavior is not modeled by this Aeneas snapshot. This is not a mismatch for the current verified 64-bit target, but 32-bit deployments would need their own model/proof or CI story.

===== AGENT 04: subtle Choice/CtOption external fidelity (II.3, VIII.1) =====
SCOPE:
Audited `subtle` 2.6.1 `Choice`, `CtOption`, `ConditionallySelectable`, `ConditionallyNegatable`, conversion/bit-op semantics, Lean models in `TypesExternal.lean`/`FunsExternal.lean`, and helioselene call sites in `field`, `point`, and `ciphersuite`.

FINDINGS: NONE

EVIDENCE:
`Cargo.lock:1566-1569` resolves `subtle` to 2.6.1. Lean models `subtle.Choice := Bool` and `subtle.CtOption T := T × Bool` at `crypto/helioselene/aeneas/HelioseleneCore/TypesExternal.lean:16-34` and `:57-74`.

Argument order matches subtle: the crate specifies `conditional_select(a,b,choice)` returns `a` for `0`, `b` for `1` at `/home/user/.cargo/.../subtle-2.6.1/src/lib.rs:393-420`; the integer implementation computes that at `:513-517`, and `Choice` delegates through `u8` at `:568-572`. Lean models this as `if c then b else a` for `Uint` at `FunsExternal.lean:837-862`, `u8` at `:2071-2087`, and `CtOption` at `:2191-2214`. Heliolselene’s field/point wrappers preserve order at `crypto/helioselene/src/field/mod.rs:58-62` and `crypto/helioselene/src/point.rs:88-95`; call sites relying on polarity are consistent, e.g. zero negation `verified/mod.rs:91-100`, identity double `point.rs:253-257`, and negative-zero rejection `point.rs:371-377`.

`CtOption` semantics match. Rust stores payload plus flag at `subtle-2.6.1/src/lib.rs:647-650`, constructs without clearing payload at `:678-683`, converts to `Option` only when `is_some().unwrap_u8() == 1` at `:652-668`, calls `map` closures on `select(default,value,flag)` at `:751-763`, calls `and_then` similarly then ANDs the flags at `:774-786`, and selects CtOptions component-wise at `:820-826`. Lean transcribes these at `FunsExternal.lean:928-930`, `:2130-2132`, `:2151-2161`, `:2179-2189`, and `:2208-2214`. Therefore `from_repr(...).and_then(...)` in `point.rs:357-378` cannot expose a noncanonical field payload from a false option; the closure may run on a dummy/default value, but the final flag remains false.

`conditional_negate` matches: subtle computes `self_neg = -self` unconditionally and assigns/selects it iff choice is 1 at `subtle-2.6.1/src/lib.rs:614-623`; Lean models `select t (-t) choice` at `FunsExternal.lean:2105-2112`. Heliolselene uses it for sqrt even-root normalization at `crypto/helioselene/src/field/verified/sqrt.rs:76-80` and decompression sign handling at `crypto/helioselene/src/point.rs:360-362`.

No reachable non-0/1 `Choice` construction found. The explicit sources are masked/shifted to one bit: `Choice::from((limb & 1) as u8)` at `verified/mod.rs:132-135`, `Choice::from(bytes[31] >> 7)` at `point.rs:349-352`, and `0.into()/1.into()` at `point.rs:367` and `:374`. Other choices come from canonical `ct_eq`/`is_odd`: subtle integer `ct_eq` returns 0/1 at `subtle-2.6.1/src/lib.rs:344-358`; crypto-bigint `CtChoice` converts through `to_u8()` at `/home/user/.cargo/.../crypto-bigint-0.5.5/src/ct_choice.rs:75-83`; `Uint::ct_eq` builds a canonical `CtChoice` at `uint/cmp.rs:52-63` and converts at `:123-127`; dalek field `ct_eq`/select delegate through crypto-bigint residue/uint code at `/home/user/.cargo/.../dalek-ff-group-0.5.0/src/lib.rs:79-90` and `/home/user/.cargo/.../crypto-bigint-0.5.5/src/uint/modular/constant_mod.rs:170-188`.

`Choice` bit operations and exits match on canonical inputs: Rust `unwrap_u8`, `From<Choice> for bool`, `bitand`, `bitor`, and `ct_eq` are at `subtle-2.6.1/src/lib.rs:122-156`, `:159-179`, and `:334-338`; Lean models them at `FunsExternal.lean:1986-2069`. `to_bytes` uses `unwrap_u8` only after `is_odd()` and zeroes the sign with canonical `x.ct_eq(ZERO)` at `point.rs:385-395`; ciphersuite decoding converts `CtOption` to `Option` only at the API boundary at `ciphersuite.rs:51-52` and `:90-91`.

`cargo test -p helioselene --lib` passed 11/11 tests.

EXPLOITABILITY / PROOF IMPACT:
No exploitable behavior or proof-invalidating model mismatch found for current code. The Bool model is faithful for all reachable, canonical `Choice` values.

If future code constructs `Choice::from(n)` with `n ∉ {0,1}`, proofs can diverge sharply from release Rust: `bool::from` treats nonzero as true, `unwrap_u8` exposes the raw byte, integer `conditional_select` uses that byte as a mask, and `CtOption -> Option` accepts exactly byte `1`. That hazard is real but not reachable in the audited helioselene sources.

RECOMMENDATIONS:
Add a small audit regression test or lint-style check covering all `Choice::from` / `into()` call sites and asserting inputs are 0/1. Keep the subtle-version pin or re-run this review on any subtle upgrade.

RESIDUAL RISK:
The existing decoded-identity/projective-representation issue noted in prior artifacts is not caused by a subtle model mismatch; the model faithfully represents the `CtOption::conditional_select` behavior used there. Residual risk is future maintenance: adding an unchecked `Choice::from` source would invalidate the Bool abstraction immediately.

===== AGENT 05: byte/limb order, shifts, remaining externals (II.4-II.6, VIII.1) =====
SCOPE:
Audited II.4-II.6 and the straightforward VIII.1 externals not already covered by Agents 03-04: endian conventions, repr serialization, `from_be_hex`, `from_le_slice`, `to_le_bytes`, `shl_vartime`/`shr_vartime`, constants, limb bit ops, wrapping add/sub, `CtOption::new`, and simple `Uint`/`CtChoice` helpers.

FINDINGS: NONE

EVIDENCE:
Cargo pins match the modeled versions: `crypto-bigint` 0.5.5 at `Cargo.lock:177-181`, `subtle` 2.6.1 at `Cargo.lock:1565-1569`.

Lean models `Uint<LIMBS>` as a little-endian limb array at `crypto/helioselene/aeneas/HelioseleneCore/TypesExternal.lean:36-55`; `toNat/ofNat` assign limb `i` weight `2^(64*i)` at `FunsExternal.lean:60-70`. This matches `crypto-bigint`’s storage, “least significant to most significant,” at `/home/user/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/crypto-bigint-0.5.5/src/uint.rs:73-75`, and `as_limbs`/`as_limbs_mut` at `uint.rs:156-164`.

Byte order matches. Rust `from_be_hex` decodes big-endian chunks and stores them into reversed limb slots at `uint/encoding.rs:37-67`; Lean parses big-endian hex at `FunsExternal.lean:458-487`. Rust `from_le_slice` writes byte chunk `i` to limb `i` using `from_le_bytes` at `uint/encoding.rs:69-90`; Lean uses little-endian `leBytesToNat` at `FunsExternal.lean:489-514`. Current Rust call sites use fixed-size inputs, so modeled panic paths are unreachable: `from_repr` passes `[u8;32]` to `U256::from_le_slice` at `crypto/helioselene/src/field/verified/mod.rs:138-155`; `to_repr` is `to_le_bytes` at `mod.rs:158-160`; `wide_reduce` slices `[u8;64]` into two 32-byte halves at `crypto/helioselene/src/field/mod.rs:177-180`; `Field::random` uses two `[u8;32]` buffers at `field/mod.rs:192-198`.

The formal repr contracts use the same convention: `from_repr_ok` proves little-endian decoding and canonicity at `Spec/Repr.lean:452-474`; `to_repr_ok` proves little-endian emission at `Spec/Repr.lean:476-480`. Supporting external lemmas are at `Spec/Externals.lean:552-580` and `:862-873`.

Big-endian hex constants are static, valid-length literals at current call sites: field modulus at `field/mod.rs:24-26`, U128 reduction constants at `field/verified/mod.rs:25-26` and `field/verified/red.rs:3-4`, invert XOR constant at `field/verified/invert.rs:127-128`, sqrt exponent at `field/verified/sqrt.rs:3-6`, and curve constants at `point.rs:450-455` and `point.rs:488-493`.

The known shift divergence is real but unreachable. Rust `Uint::shl_vartime` returns zero for `n >= Limb::BITS * LIMBS` at `uint/shl.rs:42-60`; Rust `shr_vartime` returns zero for `shift > width`, and also zero at `shift == width` because no limbs are copied, at `uint/shr.rs:48-79`. Lean instead returns `fail panic` for `s >= 64*LIMBS` at `FunsExternal.lean:604-660`. All translated production calls shift by constant `1`: field double at `field/verified/mod.rs:103-106`, invert halving at `field/verified/invert.rs:170-172`, reflected in `Funs.lean:3723-3725` and `Funs.lean:3998`. The spec only relies on shift-by-1 lemmas at `Spec/Externals.lean:487-523`.

Constants and simple ops match on the modeled 64-bit target. Rust `Limb::{ZERO,ONE,MAX,BITS}` are `0`, `1`, `Word::MAX`, `64` at `limb.rs:67-93`; Lean models them at `FunsExternal.lean:350-428`. Rust `Uint::{ZERO,ONE,LIMBS}` are `from_u8(0)`, `from_u8(1)`, and the const generic at `uint.rs:78-101`; Lean models them at `FunsExternal.lean:724-785`. Rust wrapping add/sub discard final carry/borrow at `uint/add.rs:30-32` and `uint/sub.rs:31-34`; Lean models modular addition/subtraction at `FunsExternal.lean:430-456` and `:698-722`. Limb bit ops and wrapping neg are direct word operations in `limb/bit_*.rs` and `limb/neg.rs`, matching the BitVec models at `FunsExternal.lean:98-201` and `:258-279`.

VIII.1 one-liners checked: `Uint::ct_eq` XOR-accumulates limbs at `uint/cmp.rs:50-63` and converts at `:123-127`, matching `FunsExternal.lean:1018-1039`; `const_rem` returns `(self, false)` for divisor zero in crate tests at `uint/div.rs:87-105` and `:672-676`, matching Lean’s `a % b` with `Nat % 0 = a` at `FunsExternal.lean:1041-1067`; `from_u8` places the byte in limb 0 at `uint/from.rs:5-13`, matching `FunsExternal.lean:1068-1088`; `Default` is `ZERO` at `uint.rs:208-210`, matching `FunsExternal.lean:1090-1106`. `CtOption::new` stores value and flag unchanged in Rust at `subtle/src/lib.rs:671-683`, matching the pair constructor at `FunsExternal.lean:910-930`.

EXPLOITABILITY / PROOF IMPACT:
No reachable/exploitable divergence found. The only confirmed mismatch is oversized `Uint` shifts, where Lean is conservative (`panic`) and Rust returns zero. Current proof/call sites use only `1`, so any successful Lean `ok` proof excludes the divergent region. If a future translated call site shifts by attacker-controlled or width-sized values, the model must be updated or the call guarded.

The prior malformed decoded-identity issue in `point.rs` is not duplicated here; it is not caused by byte order or external-model mismatch.

RECOMMENDATIONS:
Keep `crypto-bigint`/`subtle` pinned or re-run this audit on upgrade. Add small regression/fidelity tests for endian round trips, `from_be_hex` literal parsing, shift `1`, oversized shift behavior, and `const_rem(0)` so future model changes surface quickly. Document the oversized-shift divergence next to the Lean models.

RESIDUAL RISK:
The Lean external model is 64-bit-specific (`Limb = U64`, `BITS = 64`, `U256::LIMBS = 4`). `crypto-bigint`’s 32-bit configuration is not covered by this artifact. New call sites using large shifts or variable-length slices would need fresh review.

===== AGENT 06: raw and PrimeField constants (III.1-III.2) =====
SCOPE:
Audited raw curve/sqrt constants, `PrimeField` associated constants, and related field constants in `crypto/helioselene/src/field/mod.rs`, `field/verified/{mod,red,invert,sqrt}.rs`, and `crypto/helioselene/src/point.rs`. Checked both Helios and Selene `curve!` instantiations.

FINDINGS:

===== AGENT 14: constant-time, zeroization, compiler/codegen boundaries (VI.1-VI.3) =====
SCOPE:
Audited VI.1-VI.3 across `crypto/helioselene/src/**/*.rs`, with spot checks of `subtle 2.6.1`, `crypto-bigint 0.5.5`, `ff 0.13.1`, and `dalek-ff-group 0.5.0`. Focused on field invert/pow/sqrt, point scalar multiplication, ciphersuite hashing/decoding, zeroization, and proof/codegen boundaries.

FINDINGS:
[LOW / PROOF-SCOPE, HARDENING] Zeroization is partial and manual. The code has `Zeroize` impls, but not zeroize-on-drop for field elements/points, and several secret-bearing temporaries are left to ordinary stack/heap lifetime. This does not create an active timing leak, but it invalidates any claim that the implementation reliably clears all secret intermediates.

No new exploitable secret-dependent branch or table-index issue found in the Rust source. The prior decoded-identity bug is functional/proof-boundary relevant but not a side-channel finding, so I do not duplicate it here.

EVIDENCE:
`HelioseleneField` is `Copy` and only implements `DefaultIsZeroes`/`Zeroize`, not `ZeroizeOnDrop`: `crypto/helioselene/src/field/mod.rs:20-22`, `:49`. Points implement explicit `Zeroize` but not drop zeroization: `crypto/helioselene/src/point.rs:54-63`.

Uncleared/intermittently cleared temporaries:
- `pow` zeroizes per-window bit copies, but not the `exp` parameter or 16-entry base-power table: `field/verified/pow.rs:4-28`, `:37-47`.
- `invert` keeps secret-dependent `a,b,u,v` without clearing them: `field/verified/invert.rs:23-27`, `:184-194`.
- `sqrt` keeps `table` and `res` until return without clearing unused powers: `field/verified/sqrt.rs:9-25`, `:59-80`.
- `Field::random` leaves RNG buffers `a` and `b` uncleared: `field/mod.rs:192-198`.
- `hash_to_F` zeroizes `hash` and `uniform`, but the temporary `[dst, msg].concat()` allocation is not separately zeroized: `ciphersuite.rs:32-40`, `:71-79`.

Constant-time source structure checked:
- `u8_from_bool` uses `black_box` and zeroizes the source bit copy: `src/lib.rs:11-20`.
- Field select/reduction uses masks, fixed limb loops, and constant shifts: `field/verified/mod.rs:45-65`, `:103-106`, `:122-135`.
- `invert` runs fixed 510-step loops and uses masks/selects; debug-only `bits()` checks are under `#[cfg(debug_assertions)]`: `field/verified/invert.rs:29-33`, `:35-78`, `:89-172`, `:184-194`.
- `pow` scans all 16 entries with `conditional_select`, not a secret index: `field/verified/pow.rs:24-45`.
- `sqrt` uses direct table indices only from the public constant exponent: `field/verified/sqrt.rs:59-74`.
- Point scalar multiplication scans all precomputed entries and zeroizes the scalar copy: `point.rs:277-323`.

Dependency/codegen boundary:
- `subtle::Choice` uses best-effort optimizer barriers and documents that this is not a formal compiler guarantee: `subtle-2.6.1/src/lib.rs:102-112`, `:212-243`.
- `subtle` integer selection is mask-based: `subtle-2.6.1/src/lib.rs:511-518`.
- `crypto-bigint::Uint` selection and equality are fixed-limb loops: `crypto-bigint-0.5.5/src/uint.rs:196-205`, `uint/cmp.rs:52-63`.
- `ff::Field::pow_vartime` remains available and branches on exponent bits; no internal helioselene misuse found, but callers must not use it with secret exponents: `ff-0.13.1/src/lib.rs:170-185`.

Tests run: `cargo test -p helioselene --lib` and `cargo test -p helioselene --lib --release --no-default-features` both passed 11/11.

EXPLOITABILITY / PROOF IMPACT:
The zeroization gap is exploitable only with a separate memory-disclosure, core-dump, swap, or post-compromise memory-read primitive. It does not affect functional correctness or the Lean field/group theorems, but it means VI.2 must remain outside the proof claim.

Constant-time behavior is source-audited, not proved. The Lean model erases timing, memory access, `black_box`, volatile barriers, LLVM transforms, and hardware instruction latency. Overreading the functional proof as a constant-time or zeroization proof would be incorrect.

RECOMMENDATIONS:
Use `Zeroizing<T>` or explicit cleanup for secret temporaries in `pow`, `invert`, `sqrt`, `Field::random`, and `hash_to_F`; consider `ZeroizeOnDrop` wrappers for secret scalar/field handling where compatible with `Copy` API constraints.

Add dudect/ctgrind-style tests and assembly review for the release build tuple actually deployed. Keep proof claims phrased as functional correctness only, under pinned compiler/dependency/target assumptions.

Document `pow_vartime` as public-exponent-only for downstream users, and prefer the inherent constant-time `HelioseleneField::pow` or `ff::Field::pow` for secret exponents.

RESIDUAL RISK:
Residual VI.1/VI.3 risk is compiler, target, and microarchitecture behavior: mask code could be transformed, integer multiply/loads may have target-specific leakage, and no binary-level CT proof was performed. Zeroization remains best-effort and incomplete for intermediates.

===== AGENT 15: synthesis and risk ordering =====
SCOPE:
Reviewed the complete 15-agent assumption report, the assumption inventory, and prior local audit context. This synthesis de-duplicates inherited findings and separates exploitable issues from proof-scope and residual trust boundaries.

CONFIRMED FINDINGS:
1. [MEDIUM, high confidence] `GroupEncoding::from_bytes([0;32])` decodes the canonical identity encoding into malformed `{x:0,y:1,z:1}` instead of canonical identity `{x:0,y:1,z:0}`. This affects both Helios and Selene via the shared macro. Agents 09-11 are the same finding, not separate issues.
Impact: accepted untrusted `read_G` inputs can leave the proved group model and poison addition/MSM tables, creating verifier/reference divergence or batch-pollution risk. Direct forgery was not demonstrated because the malformed term is weighted by verifier/transcript randomness.
Proof impact: Selene group-law proof over valid `SPt` representatives remains intact, but any claim that `from_bytes/read_G` always returns a valid group element is false for `[0;32]`.

No confirmed field arithmetic, reduction, inversion, sqrt, serialization, external-model, or constant-time source-level exploit was found.

ASSUMPTIONS MATERIALly SUPPORTED:
I.1 invert step congruence: strongly supported by limb-level audit, valid-state simulation on 64/32-bit models, 510-step traces, and Dafny/reference alignment; still a Lean `sorry` until discharged.

I.2 sqrt completeness: materially supported by exact exponent reconstruction for `(p+1)/4`, table-bound analysis, random/edge tests, and final self-check. A failure would be decompression completeness/availability, not soundness.

External models II/VIII.1: crypto-bigint `sbb`, `mac`, endian conversions, `const_rem`, shifts at current call sites, and subtle `Choice`/`CtOption`/selection semantics match locked dependencies on the modeled 64-bit target.

Reducedness/constants III/IV.3: raw constants, PrimeField constants, curve constants, `from_u256`, field constructors, canonical `from_repr`, `to_repr`, bits, wide reduction, `sqrt_ratio`, equality, Sum/Product were all supported. Non-reduced `CtOption` false payloads do not escape.

Patch/tool snapshot V.3/VIII.5: source patch equivalence is materially supported for the documented 64-bit release no-default-features target.

Constant-time VI.1: source audit supports fixed schedules and no secret-dependent array index/branch in release, but this is not a formal CT proof.

RESIDUAL TRUST BOUNDARIES:
The two Lean `sorry`s remain residual formal trust despite strong audit support.

Charon/Aeneas translation, handwritten external models, source patch equivalence, native_decide validation vectors, dependency pins, compiler/codegen, and the Lean/kernel standard trust base remain outside full proof.

Proof claims apply only to the documented patched snapshot, 64-bit release, `--no-default-features`, locked dependencies. 32-bit, debug behavior, default/alloc APIs, and future dependency/compiler changes need separate review.

Helios group law, scalar multiplication, Sum, random, zeroization, ciphersuite/read_G protocol surface, and hash-to-point/generator derivation remain mostly human-audited or unmodeled.

Zeroization is partial and manual; constant-time remains compiler/microarchitecture trust. `hash_to_F` has unframed `dst || msg` but no current production Helios/Selene caller.

PRIORITIZED RECOMMENDATIONS:
1. Fix identity decoding: for `x == 0, sign == 0`, return/select `Self::identity()` or set `z = ZERO`. Add tests for both curves: `decode([0;32]) + G == G`, `G + decode([0;32]) == G`, Sum/MSM/scalar-mul behavior, negative-zero rejection, and noncanonical x rejection.

2. Add protocol defense-in-depth: reject identity at `read_G` call sites where identity is invalid, especially FCMP root-blind and proof commitment paths.

3. Discharge `step_congruence` and `sqrt_complete` in Lean, then add a theorem/validation that accepted `from_bytes` output is either canonical identity or a valid on-curve representative.

4. Keep proof claims explicitly scoped; archive regeneration artifacts and add CI for release no-default-features, dependency-fidelity tests, constant checks, and optionally 32-bit or an explicit unsupported statement.

5. Run binary-level CT tooling and improve memory hygiene with `Zeroizing`/explicit cleanup for secret temporaries.

FINAL ASSESSMENT:
The 15-agent review materially supports the core field proof assumptions and the Selene group-law theorem for valid representatives. The single actionable security-relevant defect is the decoded identity representation bug, which sits at the proof-to-protocol boundary rather than inside field arithmetic. Risk is medium, confidence high, and remediation is small. After that fix and regression coverage, remaining risk is chiefly proof-scope clarity and standard residual trust in translation, external models, compiler behavior, CT/zeroization, and unmodeled protocol-facing APIs.
