I. OPEN PROOF OBLIGATIONS (the two `sorry`s in the tree)
--------------------------------------------------------------------------------

I.1  HelioseleneSpec.Invert.step_congruence
     (HelioseleneCore/Spec/Invert.lean; one of exactly two `sorry`s in the
     tree, the other being I.2)

  ASSUMED: one iteration of the branch-free binary-GCD `step` preserves the
  Algorithm-1 invariant (b odd; u,v <= p; a = u*y and b = v*y mod p;
  gcd(a,b) = gcd(y,p)) and halves the potential (2*a'*b' <= a*b).
  Everything else about `invert` IS proved: totality (no panic, all 510
  iterations, all indexing in range), the induction assembling the 510 steps,
  the zero-input case (invert(0) yields value 0, flag false), and flag = (a != 0).

  IF FALSE: HelioseleneField::invert returns a wrong inverse for some inputs.
  Every division/normalization built on it (e.g. point decompression flows,
  batch inversion by callers) silently computes garbage. This is the classic
  failure mode of optimized constant-time GCD inverses (cf. historical bugs in
  other libraries' Bernstein-Yang implementations).

  HUMAN FOCUS: crypto/helioselene/src/field/verified/invert.rs lines ~29-182,
  specifically the mask arithmetic that (a) negates u_sub_v via XOR+carry when
  should_negate is set (lines ~111-163), (b) adds one or two copies of the
  modulus selected through MODULUS_XOR_TWO_MODULUS (lines ~127-165), and
  (c) restores bit 255 via the `add_two_modulus << 63` OR (line ~164-165).
  Cross-check: the Veridise Dafny proofs cover exactly this step
  (https://github.com/VeridiseAuditing/helioselene-dafny-proofs,
  helioselene/field/Base.dfy); eprint 2020/972 Algorithm 1 is the reference.
  Mitigating evidence: 15 end-to-end invert test vectors (random + edge cases)
  pass against independent ground truth, exercising all 510 iterations.

I.2  HelioseleneSpec.Selene.sqrt_complete
     (HelioseleneCore/Spec/Selene/Ops.lean; the second of the two `sorry`s)

  ASSUMED: completeness of the 125-iteration 4-bit-window exponentiation ladder
  in verified::sqrt — statement: for reduced a, if sqrt(a) returns (r, flag)
  and psi(a) is a square in ZMod p, then flag = true. (Functional correctness
  of the ladder: table[i] = value^i, the window loop computes
  value^((p+1)/4); since p = 3 mod 4, squaring that yields the input back on
  square inputs, so the final res^2 ct_eq value self-check succeeds.)

  NOT ASSUMED (proved, sorry-free, as sqrt_ok): the returned r is reduced and
  even, and flag = true <-> psi(r)^2 = psi(a) — the flag's SOUNDNESS comes from
  the generated code's final ct_eq self-check, independent of the ladder.

  TAINT CONE: a LEAF — nothing in the tree depends on sqrt_complete (verified
  by grep + #print axioms: only its own declaration carries sorryAx). The
  Selene group law (VIII.6) is unaffected; it never consumes sqrt. What is
  affected is DECOMPRESSION COMPLETENESS ONLY: without I.2, `flag = false`
  does not yet imply "non-square", so e.g. "from_bytes/recover_y rejects a
  well-formed compressed point only if x^3-3x+B is a non-residue" is not yet a
  theorem; accepted points are still correct (soundness is proved).

  IF FALSE (i.e. if the Rust ladder were wrong): sqrt could return flag=false
  on some square inputs — decompression would spuriously reject valid points
  (availability, not soundness). Mitigating evidence: 25 sqrt vectors
  (squares + non-squares, random + edge cases; ValidationSelene.lean) pass,
  and the Veridise Dafny scope covers sqrt (treat the Dafny proofs as the
  ladder's current story).
  HUMAN FOCUS: src/field/verified/sqrt.rs windowed loop + final window
  handling (same item as IV.1, which remains the reference for pow).

II. FIDELITY OF THE 37 EXTERNAL MODELS (crypto-bigint 0.5.5 / subtle 2.6.1)
--------------------------------------------------------------------------------

The foreign-crate primitives were NOT translated; they were re-implemented as
Lean definitions (HelioseleneCore/{Types,Funs}External.lean). All proofs are
relative to these models. Fidelity evidence is 964-vector differential testing
of the COMPOSED operations against independent big-integer semantics — strong,
but it is testing, not proof, and it validates compositions, not each primitive
in isolation. A wrong model that is compensated elsewhere, or only wrong on
untested paths, would survive. Assumptions, most subtle first:

II.1  Uint::sbb borrow conventions (FunsExternal: borrow-in is read from the
      TOP bit of the borrow limb; borrow-out is 0 or Limb::MAX as a full mask).
      IF FALSE: sub/red1/invert carry logic proofs are about different
      functions than the crate runs.
      HUMAN FOCUS: crypto-bigint-0.5.5 src/uint/sub.rs + call sites in
      src/field/verified/mod.rs (sub_value, red1) — confirm conventions.

II.2  Limb::mac = (a + b*c + carry) split into (low, high) 64-bit halves.
      IF FALSE: red512 (all multiplication) proofs are vacuous w.r.t. reality.
      HUMAN FOCUS: crypto-bigint-0.5.5 src/limb/mul.rs.

II.3  ConditionallySelectable::conditional_select(a, b, choice) returns b when
      choice = 1 (argument order!), and subtle's Choice is modeled as Bool.
      The model identifies any nonzero Choice byte with `true`; subtle's
      contract restricts Choice to {0,1} and the single constructing call site
      (is_odd) masks with `& 1`. IF a future code path constructs a Choice
      from a value outside {0,1}, model and crate diverge.
      HUMAN FOCUS: grep the crate for Choice::from / into() conversions;
      confirm every source is 0/1-valued.

II.4  Known deliberate divergence: shl_vartime/shr_vartime are modeled as
      PANIC for shift >= 64*LIMBS, whereas crypto-bigint 0.5.5 returns ZERO.
      Unreachable at every translated call site (shifts by constant 1), and
      the divergence is in the safe direction (a proof of `ok` rules it out),
      but any new call site with a large shift would be mis-modeled.

II.5  Byte/limb order conventions: little-endian limb order for Uint,
      little-endian bytes for from_le_slice/to_le_bytes, big-endian for
      from_be_hex. A consistent global flip would have been caught by the
      test vectors; a localized confusion in a rarely-used path would not.
      HUMAN FOCUS: from_repr/to_repr round-trip against the crate's
      documented canonical encoding (used in serialization -> consensus).

II.6  The remaining ~28 models (wrapping_add/sub, mul_wide, square_wide,
      bit ops, constants ZERO/ONE/MAX/BITS/LIMBS, CtOption::new) are
      straightforward, spec-lemma'd in Spec/Externals.lean, and covered by
      the semantics tables in README section 5c — a systematic 1:1 read
      against the vendored crate sources (~1-2 hours) closes this family.

III. THE REDUCEDNESS INVARIANT OUTSIDE THE VERIFIED MODULE
--------------------------------------------------------------------------------

The Field theorem lives on the carrier HField = { u : U256 // u < p }.
The proofs show the MODELED operations preserve reducedness and from_repr
rejects non-canonical encodings. But Rust-side, HelioseleneField's inner U256
is pub(crate): anything inside the crate can construct a raw field element,
and elements >= p are outside every theorem we proved (and break the
uniqueness that PartialEq/ct_eq rely on).

ASSUMED: every crate-internal construction produces a value < p.
Machine-checked for the translated ops; NOT machine-checked for:

III.1  Curve constants built with the raw constructor:
       src/point.rs:488-491 (HelioseleneField(U256::from_be_hex(...)) for the
       Selene curve parameters) and src/field/verified/sqrt.rs:4
       (MODULUS_PLUS_ONE_DIV_FOUR). A literal >= p here poisons everything
       downstream while all our theorems remain true.
       HUMAN FOCUS: check each hex literal < p (one comparison each).
       [SPOT-CHECKED 2026-07-07: all three literals verified < p numerically
       (Python, outside Lean); MODULUS_PLUS_ONE_DIV_FOUR == (p+1)/4 confirmed.
       Independent re-check still recommended.]

III.2  The PrimeField associated constants, src/field/mod.rs:234-245:
       TWO_INV, MULTIPLICATIVE_GENERATOR (=2), ROOT_OF_UNITY,
       ROOT_OF_UNITY_INV, DELTA (=4), and S=1 / NUM_BITS=255 / CAPACITY=254.
       These are claimed values, not computed: TWO_INV must equal 2^-1 mod p,
       ROOT_OF_UNITY must equal p-1 (order-2 root, since S=1), etc.
       ff-group-tests exercise them at test time; nothing in Lean does.
       HUMAN FOCUS: recompute each constant once (they are audit-relevant:
       ff's sqrt/Tonelli machinery consumes them).
       [SPOT-CHECKED 2026-07-07, numerically outside Lean: TWO_INV == 2^-1
       mod p; ROOT_OF_UNITY == p-1 and is self-inverse (matching S=1);
       2^((p-1)/2) == p-1 so 2 is a nonsquare as required of the generator;
       DELTA == 2^(2^S) == 4; NUM_BITS == 255. All < p. Independent re-check
       still recommended.]

III.3  HelioseleneField::from_u256 (src/field/mod.rs:166-168) reduces via
       crypto-bigint's const_rem — a NOT-translated, NOT-modeled reduction
       path used by the curve! macro (G_X) and available crate-wide.
       HUMAN FOCUS: confirm const_rem correctness assumptions or confine its
       use to compile-time constants that are then checked per III.1.

III.4  From<u8/u16/u32/u64> (src/field/mod.rs:28-47): trivially < p, but
       unverified; one-glance check.
