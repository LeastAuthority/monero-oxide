I. OPEN PROOF OBLIGATIONS (the two `sorry`s in the whole package)
--------------------------------------------------------------------------------

I.1  HelioseleneSpec.Invert.step_congruence  (UNCHANGED from the field ledger)
     Field-inversion GCD step invariant. Taints: HField.inv/Div, Field HField.
     DOES NOT taint the Selene group law: the group-law chain never inverts
     (projective formulas are inversion-free); #print axioms on ThetaAddEquiv
     shows no sorryAx. (Inversion IS used by ValidationSelene's checker and by
     to_bytes — see II.3.)

I.2  HelioseleneSpec.Selene.sqrt_complete  (NEW)
     (HelioseleneCore/Spec/Selene/Ops.lean)

  ASSUMED: if the input is a square mod p, the translated sqrt's validity
  flag is true. The converse — flag true implies the returned value really is
  the even-normalized square root — IS proved (sqrt_ok), because the Rust code
  ends with an explicit res^2 == input self-check; soundness needs no ladder
  analysis. Only the COMPLETENESS direction (the 125-iteration windowed
  exponentiation ladder actually computes a^((p+1)/4)) is open.

  IF FALSE: sqrt could wrongly REJECT valid square inputs. Consequence:
  point decompression (from_bytes) could reject valid encodings — a
  liveness/interoperability bug, not a soundness one (accepting a wrong point
  is excluded by the proved direction). Group law unaffected.

  HUMAN FOCUS: src/field/verified/sqrt.rs — the addition-chain preamble
  (first 128 exponent bits) and the 4-bit window loop (trigger `bits & 8`,
  final window multiply). Covered by: Veridise Dafny proofs (sqrt is a stated
  verification target), 25 sqrt test vectors incl. rejects, and the ff-group
  test suite on the patched copy.

II. WHAT THE GROUP-LAW THEOREM DOES NOT COVER (scope boundaries)
--------------------------------------------------------------------------------

II.1  Scalar multiplication. The Rust ladder (Mul<Scalar> impl, u8_from_bool/
      black_box bit handling) is deliberately untranslated (opaque). The
      `n • x` on SClass is mathlib-transported bookkeeping, NOT Rust code.
      Verifying the ladder against nsmul is the natural next stage; until
      then, ANY claim about the Rust `*` operator on points is unverified.
      HUMAN FOCUS: point.rs Mul impl (windowed ladder, table indexing,
      the (i+1)%4 window boundary logic).

II.2  The curve ORDER / the cycle property. |Selene(F_p)| = q (the 25519
      field prime) is NOT proved and is not provable with current mathlib
      (no Hasse-Weil). It remains an externally computed design fact.
      Everything proved here is order-agnostic. Note: once scalar-mul is
      verified, `q . G = O` becomes checkable computationally, which pins
      the order of <G> (and with Hasse, |E| = q — future mathlib).
      HUMAN FOCUS: the original curve-search/parameter documentation
      (tevador/kayabaNerve) for the order computation.

II.3  Encoding round-trips. from_bytes/to_bytes are translated and pass the
      test vectors, but only partial theorems exist: from_bytes completeness
      inherits sqrt_complete (I.2); to_bytes correctness (normalizes via the
      field invert) inherits step_congruence (I.1) if theoremized. No
      round-trip theorem (from_bytes ∘ to_bytes = id on classes) is proved
      yet. Encodings feed consensus — worth its own stage later.

II.4  Helios entirely (coordinates in the 25519 field; dalek boundary), plus
      point::Sum, Group::random, Zeroize, hash-to-curve (ciphersuite.rs).

II.5  Rust `sub` and `PartialEq::eq` have no dedicated test vectors; they are
      covered by kernel proofs instead (sub = add ∘ neg definitionally in the
      translation; eq = ct_eq via the proved eq_correct). Noted for
      completeness; no action needed.
