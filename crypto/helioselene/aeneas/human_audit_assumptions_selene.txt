V. STAGE-5 SCALAR-LADDER HUMAN AUDIT CHECKLIST
--------------------------------------------------------------------------------

This section is the authoritative Selene-side list of Rust changes and model
assumptions consumed by `Spec/ScalarMulLaws.lean`. The Lean theorem checks the
generated Aeneas program. It does NOT prove that the translation-only Rust
rewrite below is equivalent to production `src/point.rs`; that equivalence is
the human audit obligation recorded here and in README §4 hunk 8.

V.1  TRANSLATION COPY, NOT PRODUCTION RUST. Production `src/point.rs` remains
     the source of truth and was not changed for scalar multiplication. The
     patch is applied to a scratch copy before Charon/Aeneas and changes the
     shared `curve!` macro, hence both Selene and Helios instantiations. Human
     review must establish these four value-level equivalences:

     (a) BIT TRAVERSAL. The original
         `other.to_le_bits().iter_mut().rev().enumerate()` is replaced by
         `other.to_repr()` and indices `bit_index = 255 - i`,
         `byte_index = bit_index / 8`, `bit_offset = bit_index % 8` for
         `i = 0..255`. This relies on Selene's scalar
         `dalek_ff_group::FieldElement` having `PrimeField::Repr = [u8; 32]`
         and `PrimeFieldBits::to_le_bits()` being exactly
         `self.to_repr().into()`. Thus both spellings visit canonical
         little-endian representation bits 255, 254, ..., 0.

     (b) CONSUMED-BIT CLEANUP. The original mutable bit iterator and
         `u8_from_bool` clear each consumed Boolean in the owned `FieldBits`
         buffer. The patch clears the corresponding byte bit with the
         value-returning `clear_scalar_bit`, then explicitly zeroizes the
         complete byte array. Passing the array by value is solely a borrow-
         elimination device. Removing `u8_from_bool` also removes its
         `black_box` barriers; this is value-preserving but is NOT a proof of
         equivalent optimization resistance or memory-erasure behaviour.

     (c) LOANS AND FIXED LOOPS. The mutable 16-entry table is built in a block
         and returned immutably; table candidates are copied into locals.
         `$Point : Copy`, so coordinates are unchanged. The fixed four-double
         loop and 15-candidate scan are unrolled in the same order with the
         same indices 1..15. Every candidate remains selected using
         `usize::from(bits).ct_eq(&j)`; no secret-dependent source branch was
         introduced.

     (d) ADDASSIGN SPELLING. `res += term` becomes `res = res + term`.
         `AddAssign for $Point` in the same macro is exactly
         `*self = *self + other`, so the returned point is identical.

     The patched copy passed all 11 crate tests for both curves. That is useful
     regression evidence, not a formal equivalence proof. The failed
     unchanged-source and intermediate translations were diagnostic and are
     not part of the recorded patch.

V.2  TRANSLATOR AND GENERATED-CODE BOUNDARY. `SeleneLadder.mul_spec` is a
     theorem about the generated definitions
     `point.selene...mul`, `mul_loop`, and `mul_loop.body`, produced from the
     patched scratch copy by the pinned Charon/Aeneas/rustc versions. Correct
     correspondence to that Rust copy still relies on the unverified
     translators (README §5a). The proof unfolds or propositionally rewrites
     the exact generated bodies. Its `consumeScalarBit`, `select16`,
     `fourDoubles`, `addSelected`, and continuation-passing definitions are
     proof-only names for verbatim generated blocks; they are not replacement
     implementations. `mulP_generated` and
     `result_smul_eq_generated_rep` reconnect the quotient action to the exact
     generated result.

V.3  EXTERNAL VALUE MODELS USED BY THE SELENE LADDER.

     (a) The Rust scalar `dalek_ff_group::FieldElement` is modeled as
         `ZMod (2^255 - 19)`. Its `to_repr` model must be the canonical
         32-byte little-endian encoding of `Residue::retrieve()`, and the
         `ofZMod`/`toZMod` helpers must preserve that value. This assumption is
         load-bearing for which integer the ladder multiplies by. Unlike the
         Helios coordinate path, Selene point coordinates use the verified
         helioselene field rather than the idealized dalek field.

     (b) `usize::ct_eq` is modeled as Boolean equality, and point
         `conditional_select(A, B, choice)` is modeled componentwise as `B`
         when `choice` is true and `A` otherwise. The theorem proves the
         selected VALUE only. `Choice := Bool` erases timing, memory-access,
         volatile-read, and compiler-codegen properties.

     (c) blanket `DefaultIsZeroes::zeroize`, `[u8; 32]::zeroize`, and dalek
         scalar zeroization are modeled as pure replacement by zero. The proof
         establishes that these calls terminate and do not alter the returned
         point. It does NOT establish that secret bytes are overwritten in the
         compiled program, cannot be optimized away, or leave no copies.

     (d) Aeneas array indexing/update and machine shifts/division/remainders
         provide the functional machine model. The proof discharges all
         32-byte/16-entry bounds, all shift ranges, all 256 iterations, and
         termination relative to those models. Their fidelity, and Charon's
         release-MIR interpretation, remain inherited tool assumptions.

V.4  EXACT FUNCTIONAL CLAIM AND DOMAIN. The generic loop theorem handles every
     natural `n < 2^256`; in particular it does not assume that the top bit is
     clear. The public Selene theorem then uses canonical scalar values
     `< 2^255 - 19`. It proves table entry `j` represents `j * P`, consumes all
     256 bits in 64 four-bit windows, performs four doubles between windows
     except before the first, scans all 16 entries, and returns `n • P` without
     panic or divergence in the Aeneas model. Its point input is an `SPt`, an
     on-curve reduced representative. No claim is made for arbitrary raw or
     off-curve `SelenePoint` values accepted by Rust's public `Mul` type.

V.5  LEAN ACTION AND CURVE-ORDER BOUNDARY. Lean's `SMul` class contains an
     operation but no laws. The proof uses `Classical.choice` only to extract
     the on-curve representative whose successful generated result was already
     proved; `mulP_generated` pins that choice propositionally, with no default
     point or failure erasure. Equality with natural repeated addition gives
     `zero_smul`, `one_smul`, `smul_zero`, `smul_add`, and `DistribSMul`
     unconditionally. Scalar addition/multiplication occur modulo
     `q = 2^255 - 19`, so `add_smul` and `mul_smul` additionally require
     `SeleneExponent : ∀ P, q • P = 0`. The file proves the laws from that
     premise and exposes a certificate class, but supplies NO certificate
     instance or axiom. This is exactly the still-external order item II.2.

V.6  NON-CLAIMS AND AXIOM CONE. Neither the translation patch nor the Lean
     theorem proves constant-time execution, side-channel resistance,
     compiler preservation of the fixed scan, or physical zeroization. Kernel
     `#print axioms` confirms the ladder/action theorems use only standard Lean
     axioms plus already-recorded generated string-length constant axioms; no
     exponent certificate, `sorryAx`, or existence-only external axiom enters
     the proof cone.
