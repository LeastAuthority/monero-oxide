I. THE CENTERPIECE ASSUMPTION: THE IDEALIZED COORDINATE FIELD
--------------------------------------------------------------------------------

Unlike the Selene stage — where the coordinate field arithmetic is the
helioselene limb code we PROVED correct — the Helios coordinate field is an
IDEALIZED boundary, by design (agreed staging decision):

    dalek_ff_group.field.FieldElement := ZMod (2^255 - 19)

and the 23 operational field items the translated Helios group law references
(26 concrete defs including the toZMod/ofZMod helpers; 12 actually computed
with, the rest trait-instance evidence) are Lean definitions that are
LITERALLY the ZMod ring operations
(FunsExternal.lean, dalek section). Every headline Helios theorem is a
theorem about the group law AS IF the 25519 field arithmetic were perfect.

I.1  ASSUMED: dalek-ff-group 0.5.0's FieldElement arithmetic implements
     arithmetic in ZMod (2^255 - 19).

  WHAT THE CODE ACTUALLY IS (audit finding — sharper than folklore): the
  fidelity target is NOT curve25519-dalek. dalek-ff-group 0.5.0 implements
  FieldElement as its own type over crypto-bigint 0.5.5's constant-modulus
  MONTGOMERY RESIDUE (field.rs: 'FieldElement(ResidueType)').
  curve25519-dalek appears in the dependency tree only for dalek-ff-group's
  Ed25519/Ristretto point wrappers; no Helios field-arithmetic path touches
  it, the workspace sets no curve25519_dalek_backend cfg, and fiat-crypto's
  formally verified arithmetic is NOT in any relevant code path. The human
  obligation is therefore: review crypto-bigint 0.5.5 Montgomery Residue
  arithmetic (mul/add/sub/neg/retrieve) + dalek-ff-group 0.5.0's field.rs
  wrappers against "value semantics mod 2^255-19".

  IF FALSE: every Helios theorem is about a different curve/group than the
  code computes. This is the single largest trust item of the Helios stage.

  MITIGATIONS IN PLACE: (a) each concrete model's doc comment cites the
  exact dalek/crypto-bigint source it models, and the audit verified all 23
  operational models
  against the vendored sources — including the three subtle items:
  from_u256's reduction semantics INCLUDING inputs >= q, ct_eq's
  equal-iff-equal-mod-q argument (canonical Montgomery retrieval), and
  conditional_select's argument order; (b) the upstream crate's own test
  suite (ff-group-tests over HeliosPoint, 11/11 on the patched copy)
  exercises the real arithmetic; (c) crypto-bigint 0.5.5 Residue is widely
  used and reviewed. NOT in place: any differential test between the ZMod
  models and the real Rust field code (see I.2).

  POSSIBLE HARDENING (future): differential-test dalek-ff-group's
  FieldElement against big-int ground truth from Rust (like the crate's own
  tests, but vectorized), or replace the idealization with a verified
  limb-level model (the "full transpile + quotient" path we deliberately
  deferred).

I.2  VALIDATION SIGNAL IS WEAKER THAN SELENE'S — BY CONSTRUCTION.
