I. THE CENTERPIECE ASSUMPTION: THE IDEALIZED COORDINATE FIELD
--------------------------------------------------------------------------------

Unlike the Selene stage — where the coordinate field arithmetic is the
helioselene limb code we PROVED correct — the Helios coordinate field is an
IDEALIZED boundary, by design (agreed staging decision):

    dalek_ff_group.field.FieldElement := ZMod (2^255 - 19)

and the 23 operational field items the translated Helios group law references
(now 28 concrete dalek defs after adding canonical to_repr and zeroize; 12
actually computed with by the group law, the rest trait/scalar evidence) are
Lean definitions that are
LITERALLY the ZMod ring operations
(FunsExternal.lean, dalek section). Every headline Helios theorem is a
theorem about the group law AS IF the 25519 field arithmetic were perfect.

I.1  ASSUMED: dalek-ff-group 0.5.0's FieldElement arithmetic implements
     arithmetic in ZMod (2^255 - 19).

  WHAT THE CODE ACTUALLY IS (audit finding — sharper than folklore): the
  fidelity target is NOT curve25519-dalek. dalek-ff-group 0.5.0 implements
  FieldElement as its own type over crypto-bigint 0.5.5's constant-modulus
  MONTGOMERY RESIDUE (field.rs: 'FieldElement(ResidueType)').
  curve25519-dalek appears in the dependency tree only for dalek-ff-group's
  Ed25519/Ristretto point wrappers; no Helios field-arithmetic path touches
  it, the workspace sets no curve25519_dalek_backend cfg, and fiat-crypto's
  formally verified arithmetic is NOT in any relevant code path. The human
  obligation is therefore: review crypto-bigint 0.5.5 Montgomery Residue
  arithmetic (mul/add/sub/neg/retrieve) + dalek-ff-group 0.5.0's field.rs
  wrappers against "value semantics mod 2^255-19".

  IF FALSE: every Helios theorem is about a different curve/group than the
  code computes. This is the single largest trust item of the Helios stage.

  MITIGATIONS IN PLACE: (a) each concrete model's doc comment cites the
  exact dalek/crypto-bigint source it models, and the audit verified all 23
  operational models
  against the vendored sources — including the three subtle items:
  from_u256's reduction semantics INCLUDING inputs >= q, ct_eq's
  equal-iff-equal-mod-q argument (canonical Montgomery retrieval), and
  conditional_select's argument order; (b) the upstream crate's own test
  suite (ff-group-tests over HeliosPoint, 11/11 on the patched copy)
  exercises the real arithmetic; (c) crypto-bigint 0.5.5 Residue is widely
  used and reviewed. NOT in place: any differential test between the ZMod
  models and the real Rust field code (see I.2).

  POSSIBLE HARDENING (future): differential-test dalek-ff-group's
  FieldElement against big-int ground truth from Rust (like the crate's own
  tests, but vectorized), or replace the idealization with a verified
  limb-level model (the "full transpile + quotient" path we deliberately
  deferred).

I.2  VALIDATION SIGNAL IS WEAKER THAN SELENE'S — BY CONSTRUCTION.
  ValidationHelios.lean (75 vectors, all pass, negative controls) exercises
  the TRANSLATED GROUP-LAW CODE through the ideal models: it validates the

V. STAGE-5 SCALAR-LADDER HUMAN AUDIT CHECKLIST
--------------------------------------------------------------------------------

This is the authoritative Helios-side list for `Spec/ScalarMulLaws.lean`.
The shared mechanical patch is also recorded in the Selene ledger §V and
README §4 hunk 8. It is repeated here because an auditor must be able to assess
the Helios headline theorem from this file without silently inheriting an
unlisted Rust-code assumption.

V.1  TRANSLATION-ONLY RUST REWRITE. Production `src/point.rs` remains the
     source of truth. Charon/Aeneas were run on a scratch copy in which the
     shared `curve!` scalar ladder was rewritten only enough to avoid bitvec
     associated-type recursion and loop-carried loans. Lean proves the
     generated version; equivalence to the production spelling remains a
     human line-by-line obligation:

     (a) `other.to_le_bits().iter_mut().rev()` became direct indexing of
         `other.to_repr()` at bits 255 down to 0. For `HelioseleneField`,
         `PrimeField::Repr = [u8; 32]` and `to_le_bits()` is literally
         `self.to_repr().into()`, so both enumerate the same canonical
         little-endian bits in the same order.

     (b) the original `u8_from_bool` consumed-bit clearing became
         `clear_scalar_bit([u8; 32], byte_index, bit_offset)` plus final array
         zeroization. The helper's by-value array is only a borrow workaround.
         Removing `u8_from_bool` removes `black_box` optimization barriers;
         this is functionally value-preserving, but constant-time/codegen and
         memory-erasure equivalence are separate Rust audit obligations.

     (c) table construction now ends in a block, and each `$Point : Copy`
         candidate is placed in a local. The fixed four-double loop and the
         15 selections for indices 1..15 are unrolled in their original order.
         Every candidate is still visited through
         `usize::from(bits).ct_eq(&j)` and `conditional_select`.

     (d) `res += term` became `res = res + term`; the macro's `AddAssign`
         implementation is exactly `*self = *self + other`.

     The patched copy passed all 11 crate tests for both curves. Tests are
     regression evidence, not a proof of source equivalence. Intermediate and
     failed unchanged-source experiments are not part of the recorded patch.

V.2  GENERATED-PROGRAM CORRESPONDENCE. `HeliosLadder.mul_spec` unfolds the
     generated `point.helios...mul`, `mul_loop`, and `mul_loop.body` from the
     patched copy. Shared helper definitions in the proof (`consumeScalarBit`,
     `select16`, `fourDoubles`, `addSelected`, and CPS foldings) unfold to the
     exact right-associated blocks emitted by Aeneas; they do not substitute a
     second ladder. `mulP_generated` and `result_smul_eq_generated_rep` pin the
     quotient action back to the exact generated output. Correspondence from
     MIR/LLBC to these definitions still relies on the pinned, unverified
     rustc/Charon/Aeneas toolchain.

V.3  HELIOS-SPECIFIC VALUE-MODEL ASSUMPTIONS.

     (a) SCALAR BYTES. The Rust scalar is `HelioseleneField`. The generated
         type erases that newtype to raw `Uint 4`; its `to_repr` path is the
         translated `field::verified::to_repr` followed by concrete
         `Uint4::to_le_bytes`. The proof establishes the resulting bytes encode
         `scalar.toNat` little-endian and proves the generic loop for every raw
         `n < 2^256`. The law-bearing action deliberately restricts scalars to
         the verified reduced subtype `HField`, then invokes the generated
         function on `scalar.val`. This restriction supplies field operations
         and their value equations; it is not a change to the Rust ladder.

     (b) COORDINATE FIELD. Every table addition, doubling, and componentwise
         conditional selection computes through the idealized model
         `dalek_ff_group::FieldElement := ZMod (2^255 - 19)`. Thus the scalar
         theorem inherits the centerpiece assumption I.1 at every point
         operation, not merely at the final result. A wrong dalek/Residue model
         means the theorem verifies a different Helios curve computation.

     (c) CONSTANT-TIME PRIMITIVES. `usize::ct_eq` is modeled as Boolean
         equality; `Choice` is `Bool`; point `conditional_select(A,B,c)` is
         modeled componentwise as `B` iff `c`. These are the required value
         semantics and are enough to prove that the full scan selects table
         entry `bits`. They erase instruction timing, memory-access patterns,
         volatile reads, and optimizer behaviour.

     (d) ZEROIZATION. Blanket scalar/bit zeroization and `[u8; 32]`
         zeroization are pure models that return zeroed values. The proof shows
         the calls terminate and are functionally dead with respect to the
         point result. It does not prove an overwrite reaches physical memory,
         that the compiler retains it, or that no secret copy remains.

     (e) MACHINE OPERATIONS. Aeneas array and `U8`/`U32`/`Usize` models govern
         indexing, updates, shifts, casts, division, remainder, and release-
         mode wrapping. The proof establishes all 32-byte and 16-entry bounds,
         shift ranges, the exact 256-iteration termination measure, and absence
         of modeled panic/divergence. Fidelity of those machine models and the
         release-MIR extraction remains inherited tool trust.

V.4  EXACT CLAIM AND INPUT DOMAIN. `HeliosLadder.mul_spec` starts from an
     `HPt`, hence an on-curve representative in the verified quotient; Rust's
     raw `Mul` type itself does not enforce this and no theorem is claimed for
     arbitrary off-curve coordinates. The proof verifies every precomputation
     table entry `j * P`, all 64 four-bit windows, the skipped doubles before
     the first window, four doubles before later windows, the full 16-entry
     scan, cleanup calls, and return of `scalar.toNat • P`. It handles the full
     256-bit raw range and does not rely on a zero high bit.

V.5  `SMul`, `DistribSMul`, AND `Module` ARE DIFFERENT CLAIMS. Lean's `SMul`
     class carries only an operation. `classSmul` uses `Classical.choice` to
     extract the on-curve representative whose successful generated result is
     already proved, and `mulP_generated` fixes that representative
     propositionally; no default point or failure-erasing branch is used.
     Equality with natural repeated addition proves `zero_smul`, `one_smul`,
     `smul_zero`, `smul_add`, and `DistribSMul` without a curve-order premise.
     HField addition/multiplication reduce values modulo `p`, so `add_smul` and
     `mul_smul` additionally need
     `HeliosExponent : ∀ P, p • P = 0`. The proof constructs a `Module` from
     that premise, but provides NO `HeliosExponentCertificate` instance or
     axiom. That missing mathematical input is precisely III.2.

V.6  AXIOM-CONE DISTINCTION. The ladder theorem itself inherits only standard
     Lean axioms and the previously recorded generated Helios constant axiom.
     The conditional `moduleOfExponent` additionally computes through the
     verified `HField` field structure and therefore has the field/inversion
     proof dependencies recorded in the companion field ledger. Its exponent
     proof is an explicit theorem argument, not an axiom. None of the 39
     existence-only external axioms, no `sorryAx`, and no fabricated order
     certificate occurs in either cone. Kernel `#print axioms` commands are
     kept in `ScalarMulLaws.lean` and `AxCheck.lean` to recheck this boundary.

V.7  NON-CLAIMS. No result in this stage proves constant-time execution,
     side-channel resistance, compiler preservation of branch-free code,
     physical zeroization, equivalence of the translation patch to production
     Rust, curve cardinality, or correctness on off-curve raw inputs. These
     are intentionally visible audit/scope boundaries, not consequences to be
     inferred from the functional theorem.
